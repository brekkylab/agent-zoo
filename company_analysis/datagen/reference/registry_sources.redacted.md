# 국가별 기업 등록처 — 무엇을 붙일 수 있고 무엇은 못 붙이는가

이 데이터셋은 KR(DART) + US(EDGAR) + 전 세계(GLEIF) 세 원천만 쓴다.
일본 EDINET과 중국 CNINFO를 왜 안 썼는지, 나중에 붙인다면 어디를 잡아야 하는지 남긴다.

**결론부터**: EDINET은 붙일 만하고(코드리스트는 인증 없이 받아진다),
CNINFO는 registry로 쓸 수 없다(법인 식별자도 회사 속성도 주지 않는다).
현재 설계는 그래도 두 소스를 나중에 끼워 넣을 수 있게 되어 있다 — §4 참조.

조사 시점 2026-08-19. 응답을 직접 받아 확인했다.
개별 기업을 가리키는 값(상호·증권코드·법인번호·주소 등)은 형식만 남기고 가상값으로 바꿨다.

## 2. 일본 — EDINET / 法人番号

### 2.1 EDINETコードリスト은 인증 없이 받아진다

```
https://disclosure2dl.edinet-fsa.go.jp/searchdocument/codelist/Edinetcode.zip
→ 200, EdinetcodeDlInfo.csv, 11,383행
```

DART `corpCode.xml`에 대응하는 파일이고, **registry 레이어로 바로 쓸 수 있다.**
13개 컬럼:

```
ＥＤＩＮＥＴコード  提出者種別  上場区分  連結の有無  資本金  決算日
提出者名  提出者名（英字）  提出者名（ヨミ）  所在地  提出者業種
証券コード  提出者法人番号
```

DART 고유번호 목록보다 오히려 풍부하다 — 영문명, 업종, 자본금, 결산일이 한 파일에 있다.

**버릇** (붙일 때 걸릴 것들):

- **인코딩이 cp932(Shift-JIS)다.** UTF-8로 열면 깨진다.
- 첫 줄이 헤더가 아니라 메타 행이다 — `ダウンロード実行日,2026年08月19日現在,件数,11383件`
- **`証券コード`가 5자리다.** 도쿄증권거래소 4자리 코드(`1234`)에 `0`이 붙어 `12340`으로
  들어간다. 그대로 조인하면 안 맞는다.
- **`上場区分`이 6,281행(55%)에서 빈 문자열이다.** 상장/비상장 판정에 못 쓴다.
  DART `stock_code`가 공백 1자인 것과 같은 종류의 함정.
- `決算日`가 날짜가 아니라 `3月31日` 같은 문자열이다.
- `資本金`은 百万円 단위 정수(예: `123456`).
- **`提出者種別`에 個人이 3,152행 있다.** 법인만 거르려면 이 컬럼을 봐야 한다.
- `所在地`가 부분 주소다 — 도쿄 23구는 도도부현이 없다(`港区…１丁目１番１号`).

### 2.2 문서 API는 키가 필요하다

```
GET https://api.edinet-fsa.go.jp/api/v2/documents.json?date=...&type=2
→ 200 {"StatusCode": 401, "message": "Access denied due to invalid subscription key."}
```

HTTP는 200인데 본문에 401을 담아 준다. **상태 코드로 판정하면 안 된다** — DART가
`{"status":"013"}`을 200으로 주는 것과 같다. v1(`disclosure.edinet-fsa.go.jp/api/v1`)은
403으로 폐지됐다.

키는 무료 신청. 재무는 XBRL로 오고 DART 주요계정처럼 정제된 형태가 아니라,
파싱 비용이 DART보다 크다.

### 2.3 法人番号 Web-API — registry의 정본이지만 착수가 느리다

국세청 법인번호 공표 사이트가 일본 전체 법인(500만+)의 상호·소재지·법인번호를 준다.
EDINET 코드리스트가 공시 의무 법인 1.1만 개인 것과 대비된다.

**아플리케이션ID 발급에 2주~1개월이 걸린다.** 예제 착수 기준으로는 사실상 비용이다.
전량 CSV 다운로드도 제공되므로 API 없이도 우회는 된다.

## 3. 중국 — CNINFO는 registry로 못 쓴다

巨潮资讯网(cninfo.com.cn)은 선전거래소 지정 공시 사이트다. 확인해보면:

### 3.1 상장사 목록에 식별자가 없다

```
POST http://www.cninfo.com.cn/new/data/szse_stock.json  → 6,237건
필드: code, pinyin, category, orgId, zwjc
샘플: {"code":"000000","pinyin":"xxyh","category":"A股",
       "orgId":"gssz0000000","zwjc":"某某银行"}
```

**5개 컬럼이 전부다.** 统一社会信用代码도, 영문명도, 주소도, 업종도, 설립일도 없다.
`orgId`는 CNINFO 내부 키라 외부와 안 이어진다. registry 레이어로 쓸 수가 없다.

### 3.2 공시는 PDF만 준다

```
POST http://www.cninfo.com.cn/new/hisAnnouncement/query
→ {"secCode":"000000","secName":"某某证券",
   "announcementTitle":"…票面利率公告",
   "adjunctUrl":"finalpage/2026-08-18/0000000000.PDF",
   "adjunctType":"PDF"}
```

XBRL도 구조화 재무도 없다. `announcementTime`은 epoch millis.

### 3.3 그나마도 공식 API가 아니다

위 두 엔드포인트는 웹사이트 내부 호출이다. 약관도 안정성 보장도 없고 예고 없이 바뀐다.
공식 창구인 `webapi.cninfo.com.cn`는 등록·유료제다.

### 3.4 중국의 실제 registry는 API가 없다

국가기업신용정보공시시스템(GSXT)이 정본이지만 캡차로 막혀 있고 공개 API가 없다.
**중국 법인은 GLEIF의 `registeredAs`(统一社会信用代码 18자리)가 현실적으로 최선이다.**
픽스처가 이미 그 형식을 쓰고 있다 — `91350900MA2XKN4H7L`.

## 4. 지금 설계가 나중을 막고 있지 않다

**GLEIF `registeredAs`가 각국 등록번호를 그대로 담는다.** 이게 허브다.

| 국가 | GLEIF `registeredAs` | 대응하는 국가 등록처 필드 |
| --- | --- | --- |
| KR | `999-10-01234` | DART `bizr_no` (하이픈 없음 — 정규화 필요) |
| JP | `9190001008833` | EDINET `提出者法人番号` (13자리, 체크섬 있음) |
| CN | `91350900MA2XKN4H7L` | 统一社会信用代码 (GSXT. API 없음) |
| US | `99-0123456` | EDGAR `ein` (하이픈 없음) |

DART를 붙일 때 쓴 조인 경로(`bizr_no` ↔ `registeredAs`)가 일본에도 그대로 성립한다 —
EDINET `提出者法人番号` ↔ GLEIF `registeredAs`. **스키마를 바꾸지 않고 원천만 추가하면 된다.**

`validate.py`가 국가별 식별자 형식과 일본 法人番号 체크섬을 검사한다.
체크섬 규칙은 12자리 기준번호를 오른쪽부터 홀수 자리 ×1, 짝수 자리 ×2로 합산해
`9 - (합 mod 9)`. 공개된 실제 법인번호 2건으로 규칙을 확인했다.

---

## 5. 붙인다면 — 우선순위

1. **EDINETコードリスト** — 인증 불필요, registry에 바로 꽂힌다. 비용 대비 효과가 제일 크다.
   `datagen/reference/`에 샘플을 받아두고 cp932·5자리 증권코드·빈 `上場区分`을
   `edinet_quirks.md`로 기록하는 것부터.
2. **EDINET 문서 API** — 키 신청 후. 공시 목록·XBRL. 파싱 비용이 커서 후순위.
3. **法人番号 CSV 전량** — API 신청 대기를 피해 다운로드로. 일본 비공시 법인까지 덮어야 할 때만.
4. **CNINFO** — registry로는 권하지 않는다. 중국 공시 원문이 꼭 필요할 때 PDF 수집용으로만.

어느 것도 지금의 스키마 결정을 바꾸지 않는다. `company_index.csv`에
`edinet_code` 컬럼을 하나 더하는 것이 변경의 전부다.
